# Scraping Contract — Repository Content Specification

This document defines the expected structure and conventions for repository content that the **l-projects** scraper (`POST /repo-details/{name}/fetch`) discovers and parses. Every scraped repository should follow this contract to guarantee correct rendering on the dashboard.

---

## 1. Main Image — `project.img` / `repo_details.img`

The scraper looks for a representative screenshot in the repository.

### Discovery Order

1. `repo_details.img` — scanned from git tree paths matching patterns:
   - `screenshot.png`, `screenshot.*`
   - `mockups/screenshots/main.png`
   - `assets/screenshot.*`
   - `docs/img/header.*`
2. `project.img` — manually assigned or from `img` field during project creation.

### Contract

- The image should be a **PNG or JPEG** at least **800×600px**.
- Place it at one of the following paths for automatic discovery:
  - `mockups/screenshots/main.png`
  - `screenshot.png` (repo root)
  - `docs/img/header.png`
- Hosted URLs (GitHub raw, imgur, etc.) work for manual entry but are **not auto-discovered**.

## 2. Mockups / Features — `features_data`

The feature slider on the details page displays screenshots and descriptions of key features. Data is discovered from the `mockups/features/` directory tree.

### Directory Structure

```
mockups/
  features/
    <feature-area>/
      main.md          ← description (markdown)
      main.png         ← screenshot (image)
      <sub-feature>.md
      <sub-feature>.png
      ...
    <another-area>/
      main.md
      main.png
      ...
```

### Rules

| Element | Requirement |
|---|---|
| **Root directory** | `mockups/features/` (exact path, case-sensitive) |
| **Grouping** | Each subdirectory under `mockups/features/` becomes a **feature group**. The group label is derived from the directory name (kebab-case → Title Case). |
| **File pairing** | Every `.md` file must have a **same-named `.png`** file in the same directory. Unpaired files are ignored. |
| **`main.md` / `main.png`** | The primary screenshot and description for the group. The `main` entry is shown first. |
| **Additional files** | Additional pairs (`search.md` + `search.png`, `filters.md` + `filters.png`, etc.) are listed as sub-features within the group. |
| **Markdown content** | Describe what the feature does. First line should be a short title (rendered as bold). Include bullet points listing capabilities. |
| **Image format** | PNG only. Recommended width: **1200px**, max file size: **500 KB**. |

### Feature Data Structure (generated by scraper)

```json
[
  {
    "label": "Dashboard",
    "features": [
      { "name": "main", "img": "<raw-url>/mockups/features/dashboard/main.png", "desc": "<markdown content>" },
      { "name": "search", "img": "<raw-url>/mockups/features/dashboard/search.png", "desc": "<markdown content>" },
      { "name": "filters", "img": "<raw-url>/mockups/features/dashboard/filters.png", "desc": "<markdown content>" }
    ]
  },
  {
    "label": "Details",
    "features": [
      { "name": "main", "img": "<raw-url>/mockups/features/details/main.png", "desc": "<markdown content>" }
    ]
  }
]
```

### Example `mockups/features/dashboard/main.md`

```markdown
Main Dashboard

The primary project listing view. Displays all projects in a responsive grid of cards.

**Features:**
- Search bar with real-time filtering
- Category and skill tag filters
- Sort by name, date, or contributions
- Responsive grid layout
- Quick-access archive toggle
```

## 3. Architecture — `architecture` field

The scraper searches for architecture documentation files. The first match wins.

### Discovery Order

1. `ARCHITECTURE.md` (repo root)
2. `docs/architecture.md`
3. `docs/ARCHITECTURE.md`
4. `ARCHITECTURE.txt`

### Contract

The architecture document should include these sections:

| Section | Required | Description |
|---|---|---|
| **Overview** | Yes | 2–3 sentence summary of what the project does |
| **System Architecture** | Yes | ASCII diagram or description of component interactions |
| **Technology Stack** | Yes | Table listing languages, frameworks, databases, tools |
| **Data Flow** | Recommended | How data moves through the system |
| **Database Schema** | If applicable | Tables, columns, relationships |
| **API Endpoints** | If applicable | Key routes and their purpose |
| **Installation / Setup** | Yes | How to run the project locally |
| **Deployment** | Recommended | How to deploy to production |

### Example Structure

```markdown
# Architecture & Technology Stack

## Overview
[2-3 sentences]

## System Architecture
```
┌──────────┐    ┌──────────┐
│  Client  │───►│  Server  │
└──────────┘    └────┬─────┘
                     │
                     ▼
              ┌──────────────┐
              │  Database     │
              └──────────────┘
```

## Technology Stack
| Layer | Technology |
|---|---|
| Frontend | React 18, TypeScript |
| Backend | FastAPI (Python 3.11) |
| Database | SQLite |

## Data Flow
...

## Setup
...
```

## 4. Documentation Files — `documents` field

The scraper discovers documentation and media files across the repository. These are displayed in the Docs page reader.

### Discovery

Scanned file patterns (recursive, excluding node_modules, .git, __pycache__):
- `*.md` (excluding README.md, ARCHITECTURE.md, LICENSE.md)
- `*.mdx`
- `*.rst`
- `*.pdf`
- `*.mp4`, `*.webm`, `*.mov`

### Contract

| Element | Convention | Required |
|---|---|---|
| **Location** | `docs/` directory preferred, root-level files also discovered | — |
| **Format** | Markdown (`.md`), MDX (`.mdx`), PDF (`.pdf`) — rendered as content. Video (`.mp4`, `.webm`, `.mov`) — rendered in a `<video>` player. RST (`.rst`) supported but limited rendering. | Text docs + PDF **required**, video **optional** |
| **Frontmatter** | Optional YAML frontmatter (`--- title: ... ---`) is stripped; the filename becomes the display title (markdown only). | — |
| **PDF rendering** | PDF files are displayed via an embedded viewer using the raw GitHub URL. | Required if PDF present |
| **Video rendering** | Video files are displayed with a native `<video>` player. Recommended format: H.264 `.mp4` for broad compatibility. | Optional |
| **Images** | Use relative paths from repo root for inline images in markdown. The scraper rewrites them to raw GitHub URLs. | — |
| **Links** | Use relative intra-repo links. External links are left as-is. | — |
| **Excluded** | `README.md`, `ARCHITECTURE.md`, `docs/architecture.md`, `LICENSE*`, `CONTRIBUTING*`, `CHANGELOG*` | — |

### Document data structure (generated by scraper)

Each document entry includes:

| Field | Type | Description |
|---|---|---|
| `path` | string | Relative path from repo root (e.g. `docs/getting-started.md`) |
| `name` | string | Display title (filename without extension, prettified) |
| `content` | string | File content for text-based formats (`.md`, `.mdx`, `.rst`). Empty for binary formats. |
| `url` | string | Raw GitHub URL for binary formats (`.pdf`, `.mp4`, `.webm`, `.mov`). For text formats this mirrors the rendered GitHub URL. |

### Examples

```
docs/
  getting-started.md       ← rendered as markdown
  api-reference.md         ← rendered as markdown
  architecture-overview.pdf ← rendered in PDF viewer
  deployment-guide.pdf      ← rendered in PDF viewer
  demo.mp4                  ← rendered as video
  guides/
    authentication.md
    testing.md
    demo.webm               ← rendered as video
```

## 5. Commits — `top_commits` field

The last 5 commits are fetched directly from the **GitHub API** (`/repos/{owner}/{repo}/commits`). No repository-side configuration is needed.

### Contract

- Commits are fetched automatically — no files required.
- The scraper stores only the **most recent 5 commits**.
- Each commit includes: `sha`, `message`, `author`, `date`, `url`.

---

## 6. README — `readme` field

The README is fetched directly from the **GitHub API** (`/repos/{owner}/{repo}/readme`).

### Contract

- The file must be named `README.md` (case-insensitive) at the repository root.
- Content is base64-decoded by the scraper.
- The entire rendered content is displayed on the details page.
- No size limit enforced, but very large files (>1 MB) may impact load time.

---

## 7. Project Descriptions — `shortDescription` and `extendedDescription`

Every project provides two levels of description: a concise version for the dashboard and a full version for the detail page.

### Fields

| Field | Used In | Length | Source |
|---|---|---|---|
| `shortDescription` | Dashboard cards, list view | 1–2 sentences (max ~200 chars) | GitHub repo description (truncated if needed) |
| `extendedDescription` | Detail page "About" section | Full paragraph(s) | Manually entered via Add/Edit form; falls back to GitHub description |

### Discovery & Population

1. **`shortDescription`** — Auto-populated from the GitHub repository description during scrape (`POST /projects/batch`). If the description exceeds ~200 characters it should be truncated at the nearest sentence boundary. Repositories without a description will fall back to a derived description based on the project name, skills, and categories.

2. **`extendedDescription`** — Initially set to the same value as the GitHub description. Can be manually expanded via the Add/Edit project form on the dashboard. In future scraping passes, the scraper may attempt to extract the extended description from the first paragraph of `README.md` or the **Overview** section of `ARCHITECTURE.md`.

### Backward Compatibility

The scraper MUST always emit `description` alongside the two new fields so that older frontend clients continue to work. The `description` field holds the original GitHub description unchanged.

---

## Summary: What Each Repository Should Provide

| Artifact | Location | Auto-discovered? | Required? |
|---|---|---|---|
| README | `README.md` (root) | Yes | Strongly recommended |
| Screenshot | `mockups/screenshots/main.png` or `screenshot.png` | Yes | Recommended |
| Feature mockups | `mockups/features/<area>/{name}.md + .png` | Yes | Recommended |
| Architecture doc | `ARCHITECTURE.md` or `docs/architecture.md` | Yes | Recommended |
| Documentation (text + PDF) | `docs/*.md`, `*.pdf` | Yes | Required |
| Documentation (video) | `docs/*.mp4`, `*.webm`, `*.mov` | Yes | Optional |
| Short description | `shortDescription` — from GitHub API `description` | Yes | Strongly recommended |
| Extended description | `extendedDescription` — from GitHub API `description` (editable) | Yes | Recommended |

A repository with **no discovered artifacts** will still appear in the dashboard — it simply shows less detail.
